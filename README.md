# Б24-приложение: автозаполнение «ИНН заявителя» и «Номера протокола» из вложений

Серверное локальное приложение для облачного Битрикс24. Проходит по элементам
смарт-процесса (CRM Item, любой `entityTypeId`), достаёт вложенные файлы
(PDF / xlsx / xls / docx), извлекает из них ИНН заявителя и номер протокола,
проверяет найденный ИНН по контрольной сумме ФНС и по реестру ЕГРЮЛ/ЕГРИП
(egrul.nalog.ru) и — если всё сошлось — записывает значения обратно в карточку.
Уже заполненные поля не перезаписываются вслепую: приложение сверяет их с тем,
что реально написано в документах, и выводит расхождения в журнал для ручной
проверки.

Написано под конкретный кейс (сертификационная лаборатория), но вся
бизнес-специфика — название полей, ID сущности, список известных посредников —
вынесена в реестр профилей `LK_IFP_PROCESSES` наверху `lib/inn.php`. Приложение
умеет работать сразу с **несколькими смарт-процессами** — в интерфейсе над
полями периода есть переключатель, и каждый процесс может иметь свой набор
полей (вплоть до того, что у одного — два файловых источника с перекрёстной
сверкой, а у другого — один). Чтобы добавить свой смарт-процесс или
переключиться на другой, достаточно дописать профиль в этот реестр (см.
[«Настройка под свой смарт-процесс»](#настройка-под-свой-смарт-процесс)).

## Как это работает

1. **Источники ИНН, по приоритету** (зависят от профиля — см. ниже):
   - Поле «Файл направления» — если у процесса вообще есть такое поле
     (`direction_file_field` в профиле, может быть `null`). Обычно многозначное
     (`isMultiple`), появляется в работе раньше протокола, поэтому проверяется
     первым.
   - Поле «Файл протокола» (`protocol_file_field`) — если направление тоже
     дало результат, им **сверяется** итог; при расхождении между источниками
     побеждает протокол (как итоговый документ), но сам факт расхождения всё
     равно попадает в журнал, а не затирается тихо. У процессов с ОДНИМ
     файловым источником (`direction_file_field === null`) результат целиком
     определяется этим полем.
2. **Поиск кандидатов в тексте.** Текст, извлечённый из документа, сканируется
   на ИНН с валидной контрольной суммой (официальный алгоритм ФНС — 10 цифр
   для юрлица, 12 для ИП). Есть два класса кандидатов:
   - *«Сильный»* — число рядом с ОГРН (окно 60 символов, пара длин 13+10 или
     15+12) — такая связка почти никогда не бывает случайной.
   - *«Слабый»* — просто число нужной длины с валидной контрольной суммой, без
     привязки к ОГРН.
   Если «сильный» кандидат один — берётся он. Если кандидатов несколько без
   единственного «сильного» — берётся тот, что встречается раньше по тексту
   документа (в типовых бланках «Сведения о заявителе» идут раньше прочих
   реквизитов).
3. **Отсев заведомо чужих ИНН.** Числа рядом с меткой «орган по
   сертификации» / «орган по подтверждению соответствия» (реквизиты
   посредника, а не заявителя) и числа в контексте телефона (`+7`, «тел.»)
   исключаются из кандидатов ещё до отбора. Плюс ручной список
   `LK_IFP_EXCLUDED_INN` — ИНН конкретных посредников, которые проще
   перечислить явно, чем ловить правилами.
4. **Проверка перед записью.** Прежде чем писать найденный ИНН в карточку,
   приложение проверяет его через публичный поиск ФНС (egrul.nalog.ru) —
   структурно валидный номер мог просто не существовать в реальности. Если
   сервис недоступен (например, капча), это не блокирует запись — просто
   в журнал уходит пометка «не проверено».
5. **Аудит уже заполненных.** Если поле «ИНН Заявителя» не пусто, значение
   не трогается, но проверяется: контрольная сумма → ЕГРЮЛ → (только если
   ЕГРЮЛ недоступен) повторное извлечение из файлов и сверка. Это отдельный,
   более дешёвый путь — он не перекачивает файлы, если ЕГРЮЛ уже подтвердил
   существование ИНН.
6. **Номер протокола** обрабатывается зеркально: если поле пусто —
   заполняется из текста; если заполнено — сверяется с файлом, расхождение
   уходит в журнал без перезаписи значения.
7. **Батчинг с курсором.** Один HTTP-запрос (`ajax.php`) обрабатывает пачку
   элементов в пределах тайм-бюджета и возвращает `next_after_id` — ID
   последнего просмотренного элемента. Фронтенд (`app.js`) вызывает `ajax.php`
   по кругу, пока не придёт `done: true`. Курсор сохраняется в `localStorage`
   браузера на каждом шаге, **отдельно по каждому смарт-процессу** (ID разных
   процессов — из разных, несвязанных пространств `entityTypeId`) — если
   вкладку закрыть, сервер перезапустится или случится сетевая ошибка, прогон
   можно продолжить с того же места, а не с начала.

Результат каждого шага — пять счётчиков (`scanned` / `filled` / `ok` /
`skipped_no_file` / `problem`) и построчный журнал с деталями по каждому
элементу; журнал можно выгрузить в CSV (только проблемные строки или
полностью).

## Требования к серверу

- PHP ≥ 8.0 с расширениями `curl`, `zip`, `mbstring`, `json`, `dom`, `simplexml`.
- Утилиты в `$PATH`: `pdftotext` (пакет `poppler-utils`), `catdoc`, `xls2csv`
  (оба — из пакета `catdoc`, нужны для старого бинарного Office-формата
  `.doc`/`.xls`).
- HTTPS обязателен (Битрикс24 не откроет приложение по HTTP).
- Исходящий доступ с сервера к `*.bitrix24.ru` (REST API и скачивание файлов)
  и к `egrul.nalog.ru` (проверка ИНН).
- `memory_limit` ≥ 256M с запасом — большие вложения (особенно xlsx с крупными
  таблицами) при распаковке могут занимать на порядок больше места, чем сам
  файл; приложение отбраковывает контент крупнее ~20 МБ после распаковки
  вместо падения по памяти (см. `LkIfpOfficeZipToText`), но сам процесс всё
  равно должен укладываться в лимит.

## Установка

1. Скопировать содержимое этого репозитория в каталог сайта, например
   `/b24-inn-app/`.
2. В `config.php` указать домен портала, которому разрешён доступ
   (`IFP_ALLOWED_DOMAIN`) — запросы с любого другого домена отклоняются ещё до
   проверки токена.
3. В Битрикс24: **Разработчикам → Другое → Локальное приложение**:
   - тип — серверное, «Использует только API» — **выключено** (приложению
     нужен собственный интерфейс в iframe);
   - путь обработчика: `https://<сайт>/b24-inn-app/index.php`;
   - путь первоначальной установки: `https://<сайт>/b24-inn-app/install.php`;
   - права: **crm**, **user**;
   - сохранить → открыть приложение в разделе «Приложения».
4. Открыть приложение один раз из-под администратора портала — дальше оно
   проверяет `user.admin` на каждый запрос и не пустит никого, кроме админов.

Никаких токенов/вебхуков в коде хранить не нужно — приложение использует
текущую авторизацию пользователя-администратора из `BX24.getAuth()`
(обновляется автоматически раз в ~30 минут, см. `app.js`).

## Настройка под свой смарт-процесс

Вся привязка к конкретным CRM-сущностям и полям — в реестре `LK_IFP_PROCESSES`
в начале `lib/inn.php`. Это массив **профилей**, по одному на смарт-процесс;
ключ массива — короткий код процесса, тот же, что фронтенд шлёт в поле
`process` и что стоит значением `<option>` в переключателе на `index.php`:

```php
const LK_IFP_PROCESSES = [
	"napravlenia" => [
		"title" => "Направления",
		"entity_type_id" => 1038,
		"applicant_inn_field" => "ufCrm6_...",    // поле "ИНН заявителя"
		"direction_file_field" => "ufCrm6_...",   // поле с файлом "направления" (или null, если источник один)
		"direction_file_multiple" => true,         // isMultiple этого поля
		"protocol_file_field" => "ufCrm6_...",    // поле с файлом "протокола"
		"protocol_file_multiple" => false,         // isMultiple этого поля
		"protocol_date_field" => "ufCrm6_...",    // поле даты, по которому фильтруется период
		"protocol_number_field" => "ufCrm6_...",  // поле "номер протокола"
	],
	// "another_process" => [ ... тот же набор ключей, другие entity_type_id/коды полей ... ],
];
```

Чтобы добавить ещё один смарт-процесс:

1. Узнать `entityTypeId` и коды нужных UF-полей. Проще всего — прямо из
   браузера, пока открыто приложение (в iframe уже загружен `BX24` JS SDK
   с вашей текущей авторизацией админа): в консоли разработчика выполнить
   `BX24.callMethod('crm.type.list', {}, r => console.log(r.data()))`, найти
   нужный `entityTypeId`, затем `BX24.callMethod('crm.item.fields', {entityTypeId}, r => console.log(r.data().fields))`
   и прочитать коды полей (`ufCrm...`) из ключей объекта. Не требует ни
   вебхука, ни доступа к серверу.
2. Добавить новый элемент в `LK_IFP_PROCESSES` с этими значениями.
   `direction_file_field` можно оставить `null`, если у процесса только один
   файловый источник (с ИНН/номером работает та же логика — просто без
   перекрёстной сверки, см. `LkIfpProcessItem`).
3. Добавить `<option value="код_процесса">Название</option>` в селект
   `#process-select` в `index.php`.

Остальные функции (`LkIfpProcessItem`, `LkIfpAuditItem`,
`LkIfpVerifyOrFillProtocolNumber`, `LkIfpCountItems`, `LkIfpRunBatch`) уже
принимают профиль параметром и ничего процесс-специфичного не хардкодят —
их трогать не нужно.

Если у процесса нет отдельного поля «Номер протокола» или оно не нужно — в
профиле всё равно нужно указать какое-то существующее строковое поле
(`protocol_number_field` обязателен), либо выпилить соответствующие вызовы
`LkIfpVerifyOrFillProtocolNumber` из `LkIfpRunBatch` для этого случая.

`LK_IFP_EXCLUDED_INN` (ИНН заведомых посредников, не заявителей) — общий
для всех процессов список, не привязан к профилю.

Если документы в вашем кейсе устроены иначе (нет связки ОГРН+ИНН, другой
порядок полей, другой формат номера протокола), стоит пересмотреть
`LkIfpExtractInnCandidates`/`LkIfpExtractProtocolNumber` — регулярные
выражения там рассчитаны на типовые бланки российских протоколов испытаний/
сертификации и могут не сработать на принципиально другом шаблоне документа
(это не сломает прогон — просто кандидат не найдётся, элемент уйдёт в
`skipped_no_candidate`, а не получит неверное значение).

## Использование

В интерфейсе приложения (`index.php`):

- **Смарт-процесс** — переключатель над полями периода, список —
  `LK_IFP_PROCESSES` из `lib/inn.php`. Переключение недоступно во время
  прогона. Подписи полей периода меняются вслед за выбором (каждый профиль
  может фильтровать по своему полю даты).
- **Период** — по датам поля `protocol_date_field` выбранного профиля, либо
  «Весь смарт-процесс» (без фильтра).
- **«Заполнить ИНН»** — обычный прогон, пишет найденные значения в Б24.
- **«Сухой прогон»** — делает всё то же самое (включая скачивание и разбор
  файлов), но ничего не записывает — удобно перед большим прогоном посмотреть,
  чего ожидать.
- **«Продолжить после ID»** — возобновление с сохранённого курсора (подставляется
  автоматически, если в браузере есть незавершённый прогон).
- Журнал внизу — построчно по каждому элементу; кнопки экспортируют его в CSV
  (только проблемные строки или весь журнал).

## Известные ограничения

- **Регулярные выражения заточены под один формат документа** (см. конец
  предыдущего раздела) — при добавлении нового смарт-процесса с другим
  шаблоном документов стоит сначала прогнать «Сухой прогон» и посмотреть
  журнал: если много `skipped_no_candidate`, значит паттерны нужно
  адаптировать под новый формат, а не раз навсегда подходят любому документу.
- **ЕГРЮЛ может быть недоступен** (капча, сетевые сбои на стороне ФНС) — это
  не считается ошибкой и не останавливает прогон, но помечается в журнале как
  «не проверено».
- **Один HTTP-запрос = один шаг батча**, ограниченный временны́м бюджетом
  (см. `$timeBudgetSeconds` в `LkIfpRunBatch`, по умолчанию 22 секунды — с
  запасом до `set_time_limit` в `ajax.php`, сейчас 90 секунд). При очень
  тяжёлых документах или недоступном ЕГРЮЛ один элемент может занять заметное
  время — бюджет проверяется только *между* элементами, а не внутри обработки
  одного, так что при пограничных значениях возможен редкий таймаут. Фронтенд
  на этот случай сохраняет курсор и позволяет просто нажать запуск ещё раз.
- **Распознавание текста не идеально.** Часть протоколов кодирует кириллицу
  шрифтом с нестандартной кодировкой — `pdftotext` в таком случае отдаёт слова
  как визуально похожую латиницу («ИНН» → «HHH»). Поэтому поиск опирается в
  первую очередь на цифры (которые извлекаются надёжно), а не на слово «ИНН».
- Для старого бинарного формата Office (`.doc`/`.xls`) используется внешний
  `catdoc`/`xls2csv` — на сломанных или нетиповых файлах может не дать текста.

## Структура файлов

| Файл              | Назначение                                                        |
|--------------------|--------------------------------------------------------------------|
| `index.php`        | HTML-интерфейс приложения (открывается в iframe Б24)               |
| `install.php`      | Страница первоначальной установки (вызывает `BX24.installFinish()`)|
| `app.js`           | Фронтенд: батчинг, прогресс, резюме по курсору, экспорт CSV        |
| `ajax.php`         | Единственная точка входа для фронтенда, проверка авторизации       |
| `config.php`       | Домен портала, которому разрешён доступ                            |
| `lib/b24.php`      | Обёртка над REST Б24 (вызовы, ссылки на файлы)                     |
| `lib/inn.php`      | Вся бизнес-логика: извлечение текста, поиск ИНН/номера, батч-цикл  |
